# Przegląd projektu — listopad 2026

Świeże spojrzenie na v0.4.0 przed przeniesieniem na GitHuba i publikacją.
Punkty oznaczone `[test]` są potwierdzone testem w `server/tests/` (xfail strict).

**Werdykt w skrócie:** nie przepisywać od zera. Serwer i podstawowa pętla watchdoga są sensowne,
a wiedza o Windowsie (Session 0, taskbar, SDDL, SafeBoot) zweryfikowana na VM jest droga do odtworzenia.
Natomiast model zaufania po stronie PC dziecka ma dziury, które stają się trywialne do wykorzystania
w chwili, gdy kod jest publiczny. **Repo musi zostać prywatne do zamknięcia M1.**

## 3. Nadmiarowa złożoność

- **Cache konfiguracji** (auth 300 s, heartbeat 60 s + ręczne invalidacje). Przy 1 req/s do SQLite to mikrosekundy,
  a cache już raz spowodował błąd (invalidacja nigdy niewołana). Do usunięcia.
- **Ręczna walidacja body** w każdym endpoincie zamiast modeli Pydantic, które FastAPI daje za darmo.
- **Migracje** przez `try: ALTER TABLE … except` — przy kolejnych zmianach schematu potrzebny `schema_version`.
- **Trzy procesy, dwa mechanizmy startu, dwa pipe'y** po stronie klienta: lockscreen przez `CreateProcessAsUser`,
  tray przez Scheduled Task, osobny helper `--restore-taskbar-only`. Do tego ~190 MB (3× self-contained).
- **`IpcMessages.cs` skopiowany** do dwóch projektów — uzasadnienie w komentarzu jest nieaktualne:
  `<Compile Include="..\shared\IpcMessages.cs" Link="…" />` działa z single-file publish bez osobnej paczki.
- **~2600 linii PowerShella** (install, cleanup, offline cleanup, guardian) z całą klasą problemów
  PS 5.1 (BOM, locale, `$PSScriptRoot`). Stałe (ścieżki, entropy, nazwy) zduplikowane między PS a C#.

## 4. Decyzje do rewizji

Rekomendacja w nawiasie; **pogrubione = potrzebuję Twojej decyzji**.

1. **Awaryjne odblokowanie offline** → zamiast `emergency.dat`/`bypass.flag`: watchdog (SYSTEM) sam weryfikuje
   **ten sam TOTP** lokalnie, gdy serwer jest nieosiągalny. Sekret TOTP trafia na PC przy parowaniu,
   w pliku tylko dla SYSTEM. Lockscreen przekazuje kod przez pipe — nic nie zapisuje. Grant offline
   ograniczony (np. 60 min, kolejny kod = kolejna godzina) zamiast 24 h. Jedno poświadczenie dla rodzica.
   Koszt: dziecko-admin mogłoby wyciągnąć sekret — ale dziecko-admin i tak odinstaluje Vigila.
2. **Protokół v2**: HMAC podpisuje też request (`method|path|timestamp|nonce|sha256(body)`), bearer znika,
   jedyny sekret urządzenia leży w `signing.dat` (już SYSTEM-only). Zamyka S3 i S7 (plus zapamiętanie
   ostatniego kroku TOTP).
3. **Parowanie kodem** zamiast otwartego `claim_credentials`: panel pokazuje jednorazowy kod (np. 8 cyfr, 10 min),
   instalator go podaje, serwer generuje **nowe** klucze per parowanie. Zamyka S5.
4. **Jeden proces UI w sesji dziecka** (`vigil_ui.exe` = tray + nakładka blokady), uruchamiany i pilnowany przez
   watchdoga z utwardzonym DACL (bez `PROCESS_TERMINATE` dla użytkownika, ACE dla OWNER RIGHTS).
   Wielokrotne zabicie w krótkim czasie → watchdog wylogowuje sesję (`WTSLogoffSession`) — prosty fail-closed.
   Znika Scheduled Task „Vigil Tray”, helper taskbara i drugi pipe. Zostają 2 exe. Zamyka S4.
5. **Guardian** → usunąć. Zostaje recovery serwisu + SafeBoot w instalatorze. Wyłączanie WinRE/F8 → opcjonalna
   sekcja „utwardzanie”, w README zamiast tego: hasło BIOS + szyfrowanie dysku.
6. **Instalator w C#** (`vigil_watchdog.exe install|uninstall|repair`, `.cmd` jako cienki launcher) — jedno źródło
   prawdy dla stałych, testowalne, bez pułapek PS 5.1. Po kroku 4, nie wcześniej.
7. **Jedna instancja = jedno dziecko czy wiele urządzeń na serwer?** (rekomendacja: przed v1.0 przejść na
   jeden serwer z profilami dzieci i urządzeniami — limit liczony per dziecko, jeden panel i jeden TOTP dla
   rodzica; dla publicznego użytkownika „kontener na dziecko” to bariera). Zmienia schemat bazy, więc lepiej
   zdecydować przed M3.
8. **Język projektu** (rekomendacja: kod/komentarze/commity po angielsku, UI i README po polsku do czasu i18n,
   potem EN + PL). CLAUDE.md jest po angielsku celowo — czytany w każdej sesji, ~30% mniej tokenów.
9. **Licencja** (wstawiłem MIT; jeśli „rób co chcesz” ma być dosłowne — Unlicense/0BSD, zmiana jednego pliku).
10. Liczenie czasu: odejmować bezczynność (proces UI raportuje `GetLastInputInfo`), harmonogram per dzień
    tygodnia (7 limitów + cisza nocna), naprawa B1 przez trzymanie przedłużenia niezależnie od daty.
11. Dystrybucja: obraz serwera w GHCR + paczka klienta budowana przez CI jako asset GitHub Release.
    Exe bez podpisu kodu = ostrzeżenie SmartScreen — do opisania (podpis to koszt, nie wymóg).

## 6. Jak pracujemy, żeby nie palić tokenów

- Git zamiast ZIP-ów: sesja czyta tylko pliki, których potrzebuje; historia zastępuje sekcje typu „dawniej `agent_*`”.
- `CLAUDE.md` ma tylko inwarianty i pułapki; architektura w `docs/architecture.md` czytana na żądanie.
- Jedno zadanie = jedno issue = jeden branch/PR. Opis w issue, nie w czacie.
- Serwer weryfikowany `pytest` w sesji, klient kompilowany przez CI na `windows-latest` — koniec z wklejaniem
  błędów kompilatora. VM tylko do testów runtime.
- CLAUDE.md aktualizowany w tym samym PR, który zmienia inwariant — bez osobnego rytuału „zaktualizuj instrukcje”.
